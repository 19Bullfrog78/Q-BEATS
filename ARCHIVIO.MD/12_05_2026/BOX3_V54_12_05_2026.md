## Tech debt #14 — CHIUSO

### Implementazione

**Pattern adottato:** `didSet` sulla @Published `beatsPerBar` con guard
sull'eguaglianza `oldValue`, dispatch su `audioQueue.async` per
aggiornare mirror `_beatsPerBarQ` + chiamate C++ (`metronome_setBeatsPerBar`,
`link_engine_set_quantum`, `metronome_setAccentPattern`).

**Struttura `didSet`:**
```swift
@Published var beatsPerBar : UInt32  = 4 {
    didSet {
        guard beatsPerBar != oldValue else { return }
        guard let h = metronomeHandle else { return }
        let bpb = beatsPerBar
        let pattern = defaultAccentPattern(for: bpb)
        let mappedPattern: [UInt8] = pattern.map { $0 > 0 ? 2 : 1 }
        DispatchQueue.main.async { self.currentAccentPattern = mappedPattern }
        audioQueue.async { [h, pattern, bpb] in
            self._beatsPerBarQ = bpb
            metronome_setBeatsPerBar(h, bpb)
            if let lh = self.linkEngineHandle {
                link_engine_set_quantum(lh, Double(bpb))
            }
            pattern.withUnsafeBufferPointer { ptr in
                metronome_setAccentPattern(h, ptr.baseAddress, UInt32(pattern.count))
            }
        }
    }
}
```

**Mirror:**
```swift
// DEFAULT DEVE COINCIDERE con @Published var beatsPerBar (didSet non scatta in init)
private var _beatsPerBarQ: UInt32 = 4   // accesso SOLO su audioQueue
```

- `AudioEngine.swift:557` — `link_engine_set_quantum(lh, Double(self._beatsPerBarQ))`

## Note tecniche custodite per il futuro (delta V54)

### (NUOVO V54) Pattern mirror `*Q` per @Published audioQueue-readable

Quando una `@Published` deve essere letta su audioQueue (per
sample-accurate computation in `scheduleNextBuffer`, beat callback,
o simili), serve un mirror audioQueue-private aggiornato in
sincronia. Il pattern V20 originale (`_audioBPM`, `_clickMuted`,
`_linkMode`) usava il prefisso `_` per il mirror, ma per le @Published
**non funziona**: il property wrapper `@Published` genera
automaticamente il backing storage `_<nome>` (es. `_beatsPerBar`),
causando build rossa per collisione di nomi.

**Soluzione adottata:** suffix `Q` sul mirror (es. `_beatsPerBarQ`).
La `Q` è leggibile come "Queue" da chi legge il codice, e disambigua
dal synthesized backing storage Combine. Applicabile in futuro a ogni
nuovo mirror di @Published.

**Pin tecnico nel codice** (commento sopra la dichiarazione):
```swift
// DEFAULT DEVE COINCIDERE con @Published var beatsPerBar (didSet non scatta in init)
private var _beatsPerBarQ: UInt32 = 4   // accesso SOLO su audioQueue
```

Il default del mirror **deve** coincidere col default della @Published
perché `didSet` non scatta sull'inizializzazione di una stored
property — la sincronizzazione main→audioQueue avviene solo dal primo
cambio del Picker in poi.

### (NUOVO V54) Pattern `didSet` con `guard oldValue`

Per @Published bindate a SwiftUI `Picker` (o altri controlli che
possono scrivere lo stesso valore in cascata durante re-render), il
guard `guard <property> != oldValue else { return }` come **prima
riga assoluta** del `didSet` previene dispatch ridondanti al DSP. Da
adottare sempre quando si centralizza la propagazione in `didSet`.

Sintassi corretta Swift: `didSet` NON espone `newValue` come keyword
(esiste solo in `willSet`). Il nuovo valore è la property stessa
(es. `beatsPerBar`), il vecchio è `oldValue`.

### (NUOVO V54) Validazione test pragmatico vs chirurgico

Per validare un refactor che tocca un path Swift→C++ dove il C++ non
emette log nativi, due strade:

1. **Pragmatico (Opzione A):** validazione end-to-end con feedback
   audio/visivo. Usato per #14. Pro: nessun codice TEMP, nessun
   round-trip build. Contro: non distingue double-dispatch idempotente
   (caso che produce lo stesso stato finale ma con N+1 chiamate C++
   invece di N).

2. **Chirurgico (Opzione B):** aggiungere `os_log` TEMP nel path
   Swift, commit + push + nuovo IPA, eseguire test, commit di revert.
   Pro: distingue tutti i pattern di fallimento. Contro: ~15 min di
   round-trip, due commit extra.

**Quando preferire pragmatico:** quando il valore strutturale del
refactor è già garantito dal codice (es. assenza di race teorica) e
il double-dispatch non avrebbe effetti osservabili.

**Quando preferire chirurgico:** quando serve prova binaria per
chiusura formale di tech debt critico, o quando il test pragmatico
non può distinguere fra pass e degrade silenzioso.

### (NUOVO V54) Double-dispatch idempotente — perché Opzione A è sufficiente per #14

Nel caso specifico di #14, il rischio teorico di double-dispatch (se
il guard `oldValue` fallisse, o se `.onChange` non fosse rimosso) si
manifesterebbe come **doppia chiamata C++ con lo stesso valore di
`bpb`**. La funzione `MetronomeDSP::setBeatsPerBar` ([core_engine/MetronomeDSP.cpp:73-82](core_engine/MetronomeDSP.cpp:73)) è
**idempotente** sul pattern: scrive `_beatsPerBar = beatsPerBar`,
azzera `_currentBeatInBar`, e ri-arma `_pendingPattern` con
`memset` + scrittura del primo accento. Due chiamate consecutive con
lo stesso `beatsPerBar` producono lo stesso stato finale del DSP della
prima chiamata. Non ci sono side-effect cumulativi.

Per questa proprietà del C++ sottostante, l'Opzione A è
strutturalmente sufficiente a chiudere #14: anche se ipoteticamente
ci fossero state 2 chiamate per cambio invece di 1, l'output audio
sarebbe stato identico. Il valore architetturale del refactor (mirror
audioQueue-private, eliminazione race teorica) è già garantito dal
codice in master indipendentemente dall'osservabilità via test.

Custodito per riferimento futuro: in casi simili (refactor di
propagazione UI→DSP per funzioni C++ idempotenti), Opzione A è la
scelta corretta. Opzione B va riservata a refactor dove il C++ **non
è idempotente** o ha side-effect cumulativi.
