## Diagnosi finale Task D — Limite architetturale ABLLink App-thread

### Causa vera ratificata 12/05/2026

Documentazione ufficiale `ABLLink.h` (Ableton/LinkKit GitHub):

> "Modifying the Link session state should be done in the **audio thread**
> for the most accurate timing results. Use `ABLLinkCaptureAudioSessionState()`
> (lockfree, **audio-thread only**) to capture state, modify it, then
> `ABLLinkCommitAudioSessionState()` to apply changes with sample accuracy."

Q-B usa `ABLLinkCaptureAppSessionState` e `ABLLinkCommitAppSessionState`
(versioni **App-thread**, vedi `LinkEngine.mm:122-125` e
`link_engine_set_bpm_at_time` riga 130). Chiamate da `audioQueue`
(Swift DispatchQueue) — **NON è l'audio rendering thread reale**.

Le API "App" non sono sample-accurate per design ABLLink. Lo scarto
fisico fra "Swift audioQueue" e "audio rendering thread di sistema"
è esattamente quei ~15ms che SB percepisce come "anticipo".

### Cosa hanno risolto i 4 fix Task D

Importante: i 4 fix NON sono stati tutti "mal indirizzati". Ognuno
risolveva un problema reale e separato:

- **Task D base + fix #1 + fix #2**: risolvono problemi reali
  indipendenti dall'API ABLLink. Specificamente: broadcast ai 4
  mirror (`_audioBPM`, MIDI engine, Link, currentBPM UI) coerente
  col downbeat DSP; coerenza assert/audioBPM pre-assert; bug
  pre-esistente di salto retroattivo MIDI engine `_sampleBaseAdj`.
  Tutti restano utili indipendentemente dal limite ABLLink. Non
  revertabili.
- **Fix #3 e fix #4**: mal indirizzati sul hostTime. ABLLink applica
  `SetTempo` immediatamente — passare hostTime futuro NON ritarda
  l'applicazione né su Q-B né sui peer, è solo un riferimento di
  fase. Tentativi di calibrazione che non possono funzionare con
  l'API attualmente usata. **Restano su master come incrementi di
  precisione del hostTime passato** (sempre meglio passare un
  hostTime preciso che uno approssimato), ma non risolvono il limite
  App-thread vs Audio-thread.

### Conferma esterna

Anche Ableton Live (lo standard di riferimento per Link) presenta sync
issues con Soundbrenner Core via Link sul BPM update — fonte: Ableton
Drummer blog. Non è bug Q-B, è un comportamento noto della combinazione
App-thread ABLLink + firmware SB. Il limite v1 di Q-B è allineato con
lo stato dell'arte di mercato.

### Cosa NON è dimostrato (onestà)

Il refactor a `CaptureAudioSessionState` + render thread (tech debt
#18) **potrebbe** ridurre significativamente lo scarto, ma non è
dimostrato che lo elimini completamente. Il firmware SB ha policy
proprietarie di applicazione BPM ("1 bar wait" documentato) che
potrebbero introdurre offset indipendentemente. La validazione
definitiva sarà sul palco con setlist reali post-L1.b.

## Note tecniche custodite per il futuro (delta V52)

**(NUOVO V52) ABLLink — `App-thread` vs `Audio-thread` session state:**

ABLLink espone due famiglie di API per modificare lo stato della sessione:

1. **App-thread** (`ABLLinkCaptureAppSessionState` /
   `ABLLinkCommitAppSessionState`): chiamabile da qualsiasi thread,
   safe ma **NON sample-accurate**. Usata oggi da Q-B in
   `LinkEngine.mm` per tutte le mutazioni (`link_engine_set_bpm`,
   `link_engine_set_bpm_at_time`, `link_engine_assert_session_state`).
2. **Audio-thread** (`ABLLinkCaptureAudioSessionState` /
   `ABLLinkCommitAudioSessionState`): lockfree, **audio-thread only**,
   sample-accurate. Usata da app che vogliono cambio tempo/fase
   precisi al campione.

**Conseguenza pratica:** chiamare le mutazioni Link da `audioQueue`
Swift (anche con hostTime preciso) NON garantisce sample accuracy.
L'API ABLLink applica il cambio "immediatamente" su un thread
"App", con timing coarse di ~10-20ms vs l'audio rendering thread reale.

**Per sample accuracy:** servono le API audio-thread, chiamate
dal vero render thread (`AURenderCallback` collegato all'engine,
oppure `AVAudioSinkNode` con block che gira sull'audio thread).
Q-B oggi non ha questo accesso al render thread reale — tutto passa
da `audioQueue` (DispatchQueue serial). Per refactor vedi tech debt
#18.

**(NUOVO V52) ABLLink `SetTempo` con hostTime — chiarimento:**

Documentazione ufficiale `ABLLink.h`:

> "The change is applied immediately and sent to the network after
> committing the session state."

Il parametro `hostTime` di `ABLLinkSetTempo(state, bpm, hostTime)`
NON ritarda l'applicazione del cambio né su locale né su peer.
È solo un riferimento temporale per il calcolo della fase. Q-B
con fix #3 + #4 passa un hostTime molto più preciso (verso il vero
output del downbeat audio), ma ABLLink applica comunque immediato
sul thread App.

**Implicazione per Task D**: i fix #3/#4 hanno migliorato la
precisione del riferimento di fase passato a ABLLink, ma non
risolvono il limite App-thread. Risolvibile solo via tech debt #18.

**(NUOVO V52) Pattern di iterazione diagnostica Task D:**

5 commit incrementali sono un esempio di come affrontare un
problema multi-livello senza pezze:

1. Implementare il meccanismo base (Task D)
2. Validare su device → emerge sintomo
3. Diagnosticare la causa REALE, non assumerla
4. Fix mirato → push → re-test su device
5. Se sintomo residuo: re-diagnosticare, NON re-fixare cieco
6. Quando i fix Layer 3 esauriscono, capire se il limite è
   architetturale (Layer 1/2/altro) e documentarlo come tech debt

Ogni fix risolve un problema reale separato e va custodito anche
se non chiude completamente il sintomo finale. Niente revert
"per pulizia" se il fix risolve qualcosa di sottostante.
