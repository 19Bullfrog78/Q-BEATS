2. Durante sync skip Link (4 beat di attesa downbeat ≈ 2s a 120 BPM), DSP non sta ancora processando buffer → cambio BPM ignorato/non applicato
3. Quando il motore parte effettivamente (dopo downbeat raggiunto), il delta è già calibrato da ~1-2 secondi → vedremmo `armed audio-thread`, non `warm-up fallback`

**Validazione warm-up fallback per via alternativa:**
- Code review: branch `else` esplicito in beat callback (AudioEngine.swift:1931-1939) — chiamata `link_engine_set_bpm_at_time` quando `delta == 0`. Approvato dal referee in commit #18 base (Nota 3 — niente silent no-op)

**Conclusione:** in condizioni reali d'uso, il warm-up fallback non è mai raggiungibile. È codice difensivo per un caso edge che il design del Play (sync con Link) elimina di fatto. Resta nel codice come safety net.

## Note tecniche custodite per il futuro (delta V53)

**(NUOVO V53) Pattern audio-thread Link mutations:**

L'unico modo affidabile per chiamare le API audio-thread di ABLLink
(`ABLLinkCaptureAudioSessionState` / `ABLLinkCommitAudioSessionState`)
in un'architettura AVAudioEngine è installare un tap su un nodo del
grafo che gira sicuramente:

```swift
engine.mainMixerNode.installTap(onBus: 0, bufferSize: 512, format: nil) { _, when in
    // priorita' RT equivalente al rendering
    // niente self / weak / class Swift / ObjC msg / lock / I/O
    // chiamare le API ABLLink lockfree usando when.hostTime
}
```

**Perché mainMixerNode e non un sink:**
- AVAudioSinkNode come secondo consumer multi-destination NON viene
  invocato da AVAudioEngine runtime (bug documentato Apple Developer
  Forums, sintomi: il block ha la firma giusta, è attached, è connesso,
  ma `engine.start()` non lo schedule)
- mainMixerNode è "always-on" se engine running, il tap è invocato ad
  ogni render reale

**Perché non AURenderCallback:**
- È il pattern professional (ABLLink sample `LinkHut` usa quello)
- Costo implementazione 2-3x: bridge ObjC++/C, gestione manuale
  AudioBufferList/AudioTimeStamp, possibili interazioni fragili con
  AVAudioEngine
- Q-B non ha latency budget tight come una DAW → tap su mainMixer è
  sufficiente

**(NUOVO V53) Pattern arming audioQueue → render thread:**

Bridge atomic lockfree fra Swift audioQueue (arming pending) e tap
block (apply sample-accurate). Implementato in `QBeatsAtomics.h/.c`:

- Struct `QBeatsLinkPending` opaca (Swift OpaquePointer): contiene
  campi `_Atomic` per bpm, sample_offset, buffer_id, render_buffer_id,
  delta, sched_buffer_count, sample_rate_bits, scheduled
- audioQueue arma via `qbeats_link_pending_arm(bpm, offset, target_buffer_id)`
  → release barrier su flag `scheduled`
- Tap block legge via acquire barrier, calibra delta self-correcting
  one-shot, applica al match `renderBufferId == targetBufferId`
- Calibrazione delta `sched - render` self-correcting in ~22ms post-Play
  (race startup atteso, design referee one-shot retry)

**(NUOVO V53) Test G warm-up fallback — chiusura per design:**

Il fallback warm-up (`delta == 0` → path App-thread) è codice
difensivo che in condizioni reali d'uso NON viene mai raggiunto perché:
1. `engine.start()` avvia il rendering immediatamente
2. Il tap block calibra delta entro 1s
3. Q-B aspetta downbeat Link (4 beat di sync) prima di partire come
   metronomo
4. Quando il primo beat reale arriva, delta è già calibrato

Validazione fallback per code review + osservazione empirica nei log
pre-#18c (quando tap non si attivava, TUTTI i cambi BPM passavano per
warm-up fallback). Il path è validato funzionalmente, anche se non
riproducibile in test artificiale post-#18c.

**(NUOVO V53) Modalità aereo + Ableton Link — procedura live:**

Ableton Link gira su rete WiFi locale. Modalità aereo standard iOS
spegne WiFi → Link OFF. Per uso live con Link, procedura corretta:
1. Attiva modalità aereo
2. Da Control Center riaccendi manualmente icona WiFi
3. Connetti device al router del palco (router dedicato senza
   internet, solo LAN locale)
4. Link funziona — niente notifiche cellulari, niente interferenze

Pattern documentato Ableton/AUM/DAW pro iOS. NON è bug Q-BEATS, è
fisica del protocollo Link.

Non Disturbare o in Aereo" è incompleto per utenti Link → da
aggiornare quando si toccherà l'onboarding/popup. Vedi memoria di
