## Decisione architetturale Strada A — universal iPhone + iPad Mini + iPad

### Contesto

BOX5 V21 invariante [:416](ARCHIVIO.MD/11_05_2026/BOX5_V21_11_05_2026.md:416) dichiarava `Portrait | v1 — landscape rimandato a v2`, coerente con identità progetto "iPhone-first" [:24](ARCHIVIO.MD/11_05_2026/BOX5_V21_11_05_2026.md:24). Tuttavia la Roadmap UIUX 06/05/2026 [:153](ARCHIVIO.MD/NUOVO%20PRINCIPIO%2006_05_2026/QBEATS_Layer3_Roadmap_UIUX.md:153) aveva già programmato come Blocco 10.1 `Test suite Layer 3 — scenari device (iPhone + iPad Mini + iPad)`, intenzione mai ratificata in BOX5.

Disallineamento riemerso 12/05/2026 sera tardi durante verifica tecnica `TARGETED_DEVICE_FAMILY` in `project.yml` (non impostato → default Xcode universal `1,2` → l'app si installa già su iPad). Mauro ha esplicitato l'esigenza: Vista LIVE va letta a distanza dal palco, iPad mini sul leggio è preferibile a iPhone perché lo vedi anche con un secondo di sguardo. Target effettivi: iPhone (sviluppo + uso portable), iPad Mini (leggio piccolo), iPad Pro 12.9" (leggio fisso).

### Tre opzioni considerate (verifica con competitor)

- **AUM, Cubasis, Drambo, GarageBand:** universal con layout iPad **dedicato** (multipanel, più componenti visibili contemporaneamente). Riprogettano la UI per iPad, non scalano.
- **Soundbrenner Metronome:** universal con scaling proporzionale puro, layout identico. Funziona perché è semplice (manopola BPM + tap tempo).

Strada A (scaling proporzionale, layout identico) — pattern Soundbrenner. Costo medio.
Strada B (layout iPad dedicato multipanel) — pattern AUM/Cubasis. Costo alto, richiede design CD dedicato.
Strada C (`TARGETED_DEVICE_FAMILY: "1"` iPhone-only) — chiude porta a iPad. Costo zero ma scarta caso d'uso vero (leggio).

### Decisione ratificata

**Strada A.** App universal iPhone + iPad. Layout invariato (stessi componenti, stessa disposizione, stesse percentuali geo.size verticali). Font/spacing/elementi interattivi refattorizzati da pt assoluti a `geo.size.width * percentuale`.

Strada B non bloccata: in futuro si potrà aggiungere layout iPad dedicato per Vista LISTA / Editor canzone (dove lo spazio extra serve davvero) sopra Strada A senza riscrivere v1.

### Cosa NON cambia

- `TARGETED_DEVICE_FAMILY` resta non specificato in `project.yml`. Default Xcode `1,2` (universal). L'app si installa su iPhone + iPad senza modifiche al `project.yml`. Decisione esplicita V55.
- Layout componenti Vista LIVE invariato: header 8%, slot metronomo 10%, bar counter 8%, micro bar 4%, teleprompter 35%, macro bar 2%, NEXT 10%, handle 2%, transport 21%. Già percentuali `geo.size.height` in `LiveView.swift`.
- Portrait obbligato anche su iPad in v1. Landscape iPad ("Vista Bella v2") resta rimandato.
- Token visivi, modello dati, contratti Layer 3, invarianti audio: tutti invariati.

### Cosa cambia

- BOX5 V22 ratifica:
  - Identità progetto: "iPhone-first" → "iPhone + iPad universal portrait v1"

## Tech debt #23 — Refactor font Vista LIVE responsive

### File coinvolti (5)

- `ios_app/QBeats/UI/Live/LiveHeaderView.swift` — 8 `.font(...)` con pt assoluti
- `ios_app/QBeats/UI/Live/TeleprompterCapsuleView.swift` — 4 `.font(...)` con pt assoluti, di cui 1 con adattività ad hoc per lunghezza testo
- `ios_app/QBeats/UI/Live/POIView.swift` — 3 `.font(...)` con pt assoluti
- `ios_app/QBeats/UI/Live/TransportView.swift` — nessun font diretto, delega a RubberBtnView
- `ios_app/QBeats/UI/Live/RubberBtnView.swift` — 2 `.font(...)` con pt assoluti, di cui 1 con adattività ad hoc per lunghezza glyph

Totale: 17 callsite font da refattorizzare, in 4 file effettivi.

### Strategia

Estrarre `geo: GeometryProxy` dal `GeometryReader` già esistente in `LiveView.swift` (usato per le proporzioni layout verticali). Passarlo come parametro ai sub-View Vista LIVE. Ogni `.font(.system(size: X))` / `.font(.jbMono(.weight, size: X))` / `.font(.custom("Y", size: X))` con `X` in pt assoluti diventa:

```swift
.font(.jbMono(.bold, size: geo.size.width * percentuale))
```

dove `percentuale = X / 430` (430pt = larghezza iPhone 13 Pro portrait, baseline di calibrazione).

Calibrazione finale empirica su device, ma queste percentuali sono il punto di partenza coerente con la baseline iPhone 13 attuale.

### Vincoli architetturali

- **GeometryReader unico:** quello di `LiveView.swift` esistente. NON introdurre `GeometryReader` annidati nei singoli componenti Vista LIVE (anti-pattern SwiftUI: causa re-render eccessivi e può creare cicli di layout)
- **API vietate per scaling device-aware:**
  - `@ScaledMetric` — ancorato a Dynamic Type, non a device size
  - `UIFont.preferredFont(forTextStyle:)` — idem
  - `Font.preferredFont(...)` — idem
  - `@Environment(\.sizeCategory)` — idem
- **Quando Dynamic Type sarà utile:** se in futuro si vuole aggiungere supporto accessibility (utenti ipovedenti che alzano la dimensione testo iOS), QUELLO sarà il momento di `@ScaledMetric`, sopra il geo.size scaling. Le due esigenze (device + accessibility) si compongono per moltiplicazione, non si sostituiscono. Non è oggetto di v1.

### Estensione spacing / touch target

Stesso pattern `geo.size.width * percentuale` per:
- Spacing ≥ 20pt (es. padding orizzontale 16-32pt che separa componenti)
- Dimensioni elementi interattivi (pulsanti, slider, handle)

Spacing piccoli (< 20pt, gap interni a `HStack`/`VStack`) restano in pt assoluti — la differenza percettiva su device più grandi è trascurabile e il refactor non vale il costo.

## Note tecniche custodite per il futuro (delta V55)

### (NUOVO V55) API Dynamic Type vs device-aware scaling

API iOS che sembrano "scaling" ma sono ancorate a Dynamic Type accessibility (preferenza testo dell'utente in Impostazioni iOS, Generali → Accessibilità → Dimensioni testo):

- `@ScaledMetric` (SwiftUI property wrapper)
- `UIFont.preferredFont(forTextStyle:)` (UIKit)
- `Font.preferredFont(...)` (SwiftUI)
- `@Environment(\.sizeCategory)` (SwiftUI)

Su iPad con accessibility default = identico a iPhone con accessibility default. Non sono device-aware nel senso "lo schermo è più grande, scala tutto proporzionalmente". Servono solo per chi alza la dimensione testo iOS per leggibilità accessibility.

Per scaling device-aware in Q-BEATS (iPhone + iPad universal, leggibilità da palco) usare `geo.size.width * percentuale`. Pattern semplice, deterministico, coerente con quello già in `LiveView.swift` per le proporzioni layout verticali.

### (NUOVO V55) Audit dipendenze — fonte autoritativa per versione vendored

Per verificare la versione installata di una dipendenza in `Vendors/`:

1. **Primo step:** `git log --all --oneline -- Vendors/<nome>/`
2. **Secondo step:** Info.plist xcframework + grep header per stringhe di versione
3. **NON affidarsi:** ai commenti nel codice di consumo (`AudioEngine.swift`, `LinkEngine.mm`). Possono essere datati di settimane/mesi rispetto a un upgrade transparent

Lezione 12/05/2026 sera tardi: V54 ha registrato erroneamente `LinkKit 3.2.2` perché audit V54 ha letto i commenti codice senza fare `git log` sul vendor path. Upgrade a 4.0 era avvenuto il 05/05/2026, una settimana prima di V54.

### (NUOVO V55) Strada A vs Strada B per universal iPad

Pattern competitor pro audio iOS:

- **AUM / Cubasis / Drambo / GarageBand:** universal con layout iPad **dedicato** (Strada B). UI riprogettata per sfruttare lo spazio extra, multipanel
- **Soundbrenner Metronome:** universal con scaling proporzionale puro (Strada A). Layout identico, solo più grande

Per Q-BEATS v1: Strada A. Layout Vista LIVE è già ben pensato per leggibilità da palco a 1.5m, non beneficia particolarmente di multipanel. Risparmio: niente design CD dedicato per iPad, niente implementazione doppia. Sufficienza: leggibilità da palco su iPad mini sul leggio risolta.

Strada B resta possibile in futuro per altre viste (LISTA, Editor) dove lo spazio extra serve davvero per mostrare più informazioni contemporaneamente.
