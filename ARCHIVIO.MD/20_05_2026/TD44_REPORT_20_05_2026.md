## Bug: Ableton Link discovery QB↔QB stesso bundle ID

**Progetto:** Q-BEATS  
**Data sessione:** 20/05/2026  
**Redatto da:** Claude referee

## 1. SINTOMO

Due istanze di Q-BEATS installate su device diversi (iPhone iOS 26.5 + iPad iPadOS 18.7.9, bundle ID identico `com.bullfrog.qbeats`) **non si scoprono via Ableton Link**. Si vedono a zero peer reciprocamente.

Q-BEATS ↔ Soundbrenner funziona perfettamente sugli stessi device, stessa rete, stessa sessione.

---

## 2. PROVA DIAGNOSTICA CHIAVE

Soundbrenner su un **terzo device osservatore** vede **entrambi** i Q-BEATS come peer distinti con NodeId diversi.

Questo significa:
- I pacchetti multicast **escono correttamente** da entrambi i device Q-BEATS
- I NodeId sono **distinti** (confermato)
- Il filtering avviene sul **lato ricezione**, non in trasmissione
- Il problema **non è nel codice Q-BEATS** — è interno a `libLinkKit.a`

---

## 3. INVESTIGAZIONE CONDOTTA (sessione 18-19/05/2026 — da BOX3 V64)

### Tentativo 1 — Peer name statico via Info.plist
`ABLLinkPeerName: "Q-BEATS"` in `project.yml > info.properties` (commit `4639efc`)  
**Esito:** cosmético, non influisce sul discovery. Nome identico su entrambi i device.

### Tentativo 2 — Chiavi Info.plist statiche aggiuntive (commit `2b379e4`)
4 chiavi aggiunte: `ABLLinkPeerName`, `ABLLinkStartStopSyncSupported`, `NSLocalNetworkUsageDescription`, `NSBonjourServices`  
**Esito:** INERTE. XcodeGen mergia `project.yml` sopra il plist statico — per chiavi duplicate, `project.yml` vince. Confermato empiricamente dal testo del prompt locale network usato da iOS al primo lancio.

### Tentativo 3 — Runtime override peer name (commit `5dc1499`)
`ABLLinkSetPeerName` (API undocumented trovata nei simboli di `libLinkKit.a`) chiamata runtime con `UIDevice.current.name`. Peer diventano "iPhone" e "iPad" — nomi distinti, visibili nel pannello ABL.  
**Esito:** Non risolutivo. Discovery QB↔QB ancora fallisce nonostante nomi distinti.

### Tentativo 4 — Upgrade LinkKit 4.1 beta 1 (verificata 19/05/2026)
Diff `e9a2e414..be64e5d1` esaminato: tocca ONLY `link_audio/*` + esempio demo.  
**Zero modifiche al discovery layer** (`include/ableton/discovery/*`, `Peers.hpp`, `NodeId.hpp`, `Controller.hpp`).  
**Decisione:** NON aggiornare. Non risolverebbe.

---

## 4. ANALISI SOURCE CODE Ableton/link (open source)

- **`NodeId.hpp`**: NodeId è `std::array<std::uint8_t, 8>` riempito da PRNG `std::mt19937` seedato con `std::random_device` (vera entropia hardware su iOS via `arc4random`/`SecRandomCopyBytes`)
- **Conclusione:** NodeId 100% random non-deterministico. Due installazioni su device diversi **devono** generare NodeId distinti.
- **Ipotesi NodeId collision: SMENTITA** dal source code e confermata dalla prova SB-osservatore.

---

## 5. SIMBOLI UNDOCUMENTED TROVATI IN libLinkKit.a 4.0

Estratti via PowerShell (`[System.Text.Encoding]::ASCII.GetString`):

- `_ABLLinkSetPeerName` — API C esportata, non documentata in `ABLLink.h`
- `__ZN7ABLLink11setPeerNameEPKc` — mangled C++: `ABLLink::setPeerName(char const*)`
- `__ZN12_GLOBAL__N_115defaultPeerNameEv` — default "Link App"
- `_OBJC_CLASS_$_NSUserDefaults` + `_objc_msgSend$standardUserDefaults` — LinkKit persiste stato internamente via UserDefaults

## 7. CAUSA PIÙ PROBABILE RESIDUA

**Filtro interno a `libLinkKit.a 4.0`** — check tipo `if peer.bundleId == self.bundleId → skip`, progettato per filtrare l'eco di se stessa su stesso device, applicato erroneamente cross-device.

Non investigabile direttamente: il binary è chiuso.

## 8. DOMANDA APERTA CRITICA — di chi è il problema?

La domanda non è ancora risolta: il filtro è in **LinkKit (Ableton)** o in **iOS (Apple)**?

iOS da versione 14 ha un sistema di sandboxing e permessi multicast che potrebbe applicare autonomamente un filtro a livello kernel/networking per pacchetti tra istanze della stessa app su rete locale.

**Come verificarlo:**
1. Installare **LinkHut** (app demo open source Ableton, bundle ID `com.ableton.LinkHut`) su due device diversi → se non si vedono, il problema è in LinkKit. Se si vedono, il problema è specifico a qualcosa in Q-BEATS.
2. Testare due app qualsiasi con multicast puro (senza LinkKit) stesso bundle ID → se non si vedono, il problema è iOS.

## 11. SOLUZIONI VALUTATE

### Soluzione A — Aspettare risposta Ableton ✅ IN CORSO
Costo zero. Se confermano bug e forniscono fix o workaround ufficiale, risolve tutto senza toccare l'architettura. **Prima scelta.**

### Soluzione B — Due bundle ID via build configuration ⚠️ SCARTATA PER USO COMMERCIALE
Tecnicamente fattibile in `project.yml` con XcodeGen. iPhone = `com.bullfrog.qbeats`, iPad = `com.bullfrog.qbeats.ipad`. Per LinkKit sono app diverse, filtro non scatta.  
**Problemi commerciali:**
- Richiede due App Store listing o almeno due App ID
- Dati non condivisi tra le due installazioni (setlist, canzoni, config su container iOS separati)
- L'utente deve sapere quale delle due app installare su quale device
- Non professionale per un'app commerciale: un musicista compra Q-BEATS e deve funzionare, punto.  
**Uso ammesso:** solo come workaround temporaneo per test di sviluppo, non come soluzione di prodotto.

### Soluzione C — Sistema sync proprietario QB↔QB ✅ SOLUZIONE COMMERCIALE DEFINITIVA (futuro)
Come Stage Traxx: protocollo host/client proprietario via Wi-Fi locale, indipendente da Link e da bundle ID. Un device fa da master, gli altri si collegano come client.  
**Vantaggi:** unica app, unico bundle ID, trasparente per l'utente, nessun limite bundle ID.  
**Costo:** feature di Fase 6-7, richiede progettazione protocollo di rete dedicato. Non per v1.
