## Esiti test #308 (post-revert) — dato nuovo

Test in condizioni reali con Soundbrenner connesso e fermo:

- **Comportamento osservato:** all'avvio Q-BEATS a volte parte immediatamente, a volte con ritardo variabile. Quando il ritardo è presente, il **beat 2 fa "saltino" (BUG-LINK-A)**. Quando parte subito, il beat 2 è pulito.

- **Diagnosi della correlazione (validata da 3 prospettive indipendenti):**
  - Il **DOWNBEAT WAIT** in `AudioEngine.swift:343-374` aspetta il prossimo downbeat della timeline Link prima di partire.
  - Se la fase Link al momento del play è ≈ 0 → no attesa → la sessione condivisa è in stato pulito → δ ≈ 0 → `sync_phase` non corregge → beat 2 pulito.
  - Se la fase Link è 0.5 o 0.9 → DOWNBEAT WAIT attende → la sessione è già negoziata con il peer → δ > 0.01 beat → `sync_phase` corregge al buffer #4 → **beat 2 saltella**.
  - Correlazione perfetta tra "ritardo all'avvio" e "saltino beat 2": **stessa causa unica**, non due fenomeni.

- **Conclusione:** BUG-LINK-A NON è risolto da #306. Il fix temporale in `sync_phase` era necessario ma insufficiente. Il bug è intermittente e correlato alla fase Link al momento del play. Inaccettabile per uso live.

## Causa di fallimento di #307

#307 sostituiva `link_engine_set_is_playing` con 4 funzioni semantiche + 1 probe.
Il branching in `AudioEngine.swift` era:

```swift
if !probe.isPlaying {
    link_engine_start_at_beat_zero(lh, hostNow)   // master path
} else {
    // quantized launch                            // follower path
}
```

Errore: nel caso "Q-BEATS master + Soundbrenner connesso ma FERMO" il branch
preso era master (`isPlaying == false`). `start_at_beat_zero` chiede a Link
di mappare beat 0 a hostTime, **sovrascrivendo** la timeline condivisa.
Soundbrenner aveva già una timeline interna negoziata → loop di rinegoziazione
→ `sync_phase` corregge ripetutamente con valori oscillanti → MetronomeDSP
riceve `setBeatPosition` impazziti → distorsione audio + beat random.

## Lezione architetturale

La doc Ableton LinkKit dice:

> "When joining an existing Link session, an app should adjust to the existing
> session's tempo and phase, which will usually result in a beat time jump."
>
> "Apps that are already in a session should never have any kind of beat time
> or audio discontinuity when a new participant joins the session."

Interpretazione corretta: **"already in a session" significa "presente nella
sessione", NON "in play"**. Soundbrenner connesso ma fermo è già nella
sessione. Q-BEATS è il nuovo arrivato e deve adeguarsi, anche se Soundbrenner
non sta playing.

Quindi `start_at_beat_zero` (Q-BEATS detta la timeline) è valido **solo**
quando Q-BEATS è solo nella sessione Link (peers == 0).

## Piano #309 — modello a 3 rami

| numPeers | probe.isPlaying | Azione |
|---|---|---|
| 0 | false | `link_engine_start_at_beat_zero` (Q-BEATS detta) |
| > 0 | false | quantized launch (master con peer fermo) |
| > 0 | true | quantized launch (follower con peer in play) |

Casi 2 e 3 condividono implementazione: aspettare downbeat,
`link_engine_join_running_session(futureHostTime)`, NESSUN RequestBeatAtTime.
Link gestisce internamente la differenza tra peer fermo e peer in play.

### BUG-LINK-BACKGROUND (Fase 2, aperto)

**Sintomo:** quando lo schermo del cellulare si spegne (idle timer iOS), il
peer Link di Q-BEATS cade. Soundbrenner mostra popup "no Link". Q-BEATS
rientrato vede il toggle Link ancora ON ma `numPeers = 0`.

**Causa identificata:** Q-BEATS ha `UIApplication.shared.isIdleTimerDisabled = true`
SOLO durante `start()` (riga 358 di `AudioEngine.swift`) e lo riabilita a
`false` nello `stop()` (riga 1014). Quando il metronomo è fermo:
1. Schermo si spegne dopo timeout iOS (~30 sec)
2. Audio engine fermo + schermo off → iOS sospende il networking dell'app
3. Socket multicast UDP di Link viene chiuso
4. `numPeers` collassa a 0 ma `linkEnabled` (toggle UI) resta `true`

Soundbrenner non ha il problema perché tiene `isIdleTimerDisabled = true`
sempre quando in foreground, indipendentemente dallo stato transport.

**Fix approvato (TASK-LINK-IDLE-TIMER):** vedi sotto. Chiude PARZIALMENTE:
risolve il caso "schermo si spegne", NON il caso "utente switcha ad altra
app" (background vero, dove iOS resetta comunque idle timer e cade il
networking — comportamento accettabile per ora).

### TASK-LINK-PREFPANE (Fase 2, aperto)

**Problema:** il preference pane ufficiale `ABLLinkSettingsViewController`
(wrappato in `LinkSettingsPresenter`) è raggiungibile **solo la prima
volta** che l'utente abilita Link. Le volte successive il toggle in
`SettingsView` bypassa il pane e va direttamente a `setLinkEnabled`.
Viola la compliance LinkKit (il pane deve essere accessibile sempre).

**Codice attuale** (`SettingsView.swift:25-33`):
```swift
Toggle("Link", isOn: Binding(
    get: { audioEngine.linkEnabled },
    set: { newValue in
        if newValue,
           let p = audioEngine.linkSettingsPresenter,
           !p.ablIsEnabled() {       // ← solo la prima volta
            showLinkSetup = true
        } else {
            audioEngine.setLinkEnabled(newValue)  // bypassa il pane
        }
    }
))
```

**Fix approvato (~5 righe):** aggiungere row dedicata "Apri impostazioni
Link" in `SettingsView` che imposta `showLinkSetup = true` sempre. Il
toggle custom resta come shortcut. Conforme alle linee guida Ableton.

```swift
SwiftUI.Section("Ableton Link") {
    Toggle("Link", isOn: ...)              // resta
    if let p = audioEngine.linkSettingsPresenter {
        Button("Apri impostazioni Link") {
            showLinkSetup = true
        }
    }
    HStack { Text("Peers"); ... }          // resta
    HStack { Text("BPM"); ... }            // resta
}
```

### TASK-LINK-IDLE-TIMER (Fase 2, aperto, chiude parzialmente BUG-LINK-BACKGROUND)

**Policy ratificata 07/05/2026 (Mauro):** lo schermo deve sempre restare
acceso quando Q-BEATS è in foreground, indipendentemente dallo stato
transport. Coerente con use case live (batterista sul palco) e con
Soundbrenner stesso. NESSUNA opzione configurabile in Settings — su un'app
live questa decisione la prende l'app, non l'utente.

**Fix (~5 righe):**
1. Aggiungere `onAppear` / `onDisappear` nella root view (`AppRootView`
   o `ContentView`):
```swift
.onAppear {
    UIApplication.shared.isIdleTimerDisabled = true
}
.onDisappear {
    UIApplication.shared.isIdleTimerDisabled = false
}
```
   Il `false` in `onDisappear` è teoricamente ridondante (iOS resetta in
   background), ma esplicitato per leggibilità.

2. **Rimuovere** `UIApplication.shared.isIdleTimerDisabled = true` da
   `AudioEngine.swift:358` (`start()`).

3. **Rimuovere** `UIApplication.shared.isIdleTimerDisabled = false` da
   `AudioEngine.swift:1014` (`stopSync()`).

Evita doppio set, gestione centralizzata sulla view root.
