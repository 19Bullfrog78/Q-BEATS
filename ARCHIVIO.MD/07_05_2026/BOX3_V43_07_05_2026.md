## Esiti test #308 (post-revert) — dato nuovo

Test in condizioni reali con Soundbrenner connesso e fermo:

- **Comportamento osservato:** all'avvio Q-BEATS a volte parte immediatamente, a volte con ritardo variabile. Quando il ritardo è presente, il **beat 2 fa "saltino" (BUG-LINK-A)**. Quando parte subito, il beat 2 è pulito.

- **Diagnosi della correlazione (validata da 3 prospettive indipendenti):**
  - Il **DOWNBEAT WAIT** in `AudioEngine.swift:343-374` aspetta il prossimo downbeat della timeline Link prima di partire.
  - Se la fase Link al momento del play è ≈ 0 → no attesa → la sessione condivisa è in stato pulito → δ ≈ 0 → `sync_phase` non corregge → beat 2 pulito.
  - Se la fase Link è 0.5 o 0.9 → DOWNBEAT WAIT attende → la sessione è già negoziata con il peer → δ > 0.01 beat → `sync_phase` corregge al buffer #4 → **beat 2 saltella**.
  - Correlazione perfetta tra "ritardo all'avvio" e "saltino beat 2": **stessa causa unica**, non due fenomeni.

- **Conclusione:** BUG-LINK-A NON è risolto da #306. Il fix temporale in `sync_phase` era necessario ma insufficiente. Il bug è intermittente e correlato alla fase Link al momento del play. Inaccettabile per uso live.

## Causa di fallimento di #307

#307 sostituiva `link_engine_set_is_playing` con 4 funzioni semantiche + 1 probe.
Il branching in `AudioEngine.swift` era:

```swift
if !probe.isPlaying {
    link_engine_start_at_beat_zero(lh, hostNow)   // master path
} else {
    // quantized launch                            // follower path
}
```

Errore: nel caso "Q-BEATS master + Soundbrenner connesso ma FERMO" il branch
preso era master (`isPlaying == false`). `start_at_beat_zero` chiede a Link
di mappare beat 0 a hostTime, **sovrascrivendo** la timeline condivisa.
Soundbrenner aveva già una timeline interna negoziata → loop di rinegoziazione
→ `sync_phase` corregge ripetutamente con valori oscillanti → MetronomeDSP
riceve `setBeatPosition` impazziti → distorsione audio + beat random.

## Lezione architetturale

La doc Ableton LinkKit dice:

> "When joining an existing Link session, an app should adjust to the existing
> session's tempo and phase, which will usually result in a beat time jump."
>
> "Apps that are already in a session should never have any kind of beat time
> or audio discontinuity when a new participant joins the session."

Interpretazione corretta: **"already in a session" significa "presente nella
sessione", NON "in play"**. Soundbrenner connesso ma fermo è già nella
sessione. Q-BEATS è il nuovo arrivato e deve adeguarsi, anche se Soundbrenner
non sta playing.

Quindi `start_at_beat_zero` (Q-BEATS detta la timeline) è valido **solo**
quando Q-BEATS è solo nella sessione Link (peers == 0).

## Piano #309 — modello a 3 rami

| numPeers | probe.isPlaying | Azione |
|---|---|---|
| 0 | false | `link_engine_start_at_beat_zero` (Q-BEATS detta) |
| > 0 | false | quantized launch (master con peer fermo) |
| > 0 | true | quantized launch (follower con peer in play) |

Casi 2 e 3 condividono implementazione: aspettare downbeat,
`link_engine_join_running_session(futureHostTime)`, NESSUN RequestBeatAtTime.
Link gestisce internamente la differenza tra peer fermo e peer in play.

  quantized launch quando non serve = ritardo di una battuta. Zero distorsione.

  fire, ma Q-BEATS ha già deciso di adeguarsi. Parte allineato al downbeat
  della timeline Link interna. Coerente.
